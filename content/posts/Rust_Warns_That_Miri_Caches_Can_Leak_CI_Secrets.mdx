On September 21, the Rust Security Response Team published a warning about a CI pitfall: Miri, the Rust interpreter for detecting undefined behavior, stored every environment variable in the `target/` directory. When a workflow caches `target/`, secrets from that environment can end up in the cache. The team said this is not a vulnerability by itself, but it becomes exploitable when combined with GitHub Actions caching behavior.

## What went wrong

According to the Rust blog, Miri wrote all environment variables to `target/` so it could retain build-relevant ones across its multiple invocations under `cargo miri`. That included any secrets present.

The attack path the team describes relies on normal repository setups:

- Workflows on `main` typically write to the cache, while pull requests can only read from it, which prevents cache poisoning.
- Anyone who has previously landed a change can open a PR and trigger CI after the first approval, and later PRs rerun CI automatically.
- An attacker could run a CI job that reads secrets from the cached `target/` directory, then push a second commit to hide the activity.
- GitHub may hide overwritten commits, and CI logs and old commits are deleted after a few months, which makes detection harder.

## Are you affected?

The team says you are likely vulnerable if all of these hold:

- You run `cargo miri` in CI.
- The step running Miri has access to secrets, whether passed directly, set in workflow-level `env`, or persisted by an earlier step.
- The workflow caches `target/`, commonly via `actions/cache` or `swatinem/rust-cache`.
- Pull requests can access that cache, which is the typical setup.

The team's ecosystem scan found one vulnerable GitHub repository and seven others that appeared safe but were advised to be cautious. It cautioned the scan may be incomplete.

## The fix and what to do

Miri now preserves only `CARGO_*` variables (excluding `CARGO_*_TOKEN`) and `OUT_DIR`. The fix is in a Miri pull request and, per the post, is included in the 2026-09-22 nightly. For users, the team recommends:

- Disable caching for affected jobs, limit secrets to steps that do not run Miri, or temporarily disable Miri.
- Clear the cache.
- Consider rotating any secrets that may have leaked.

## The broader lesson

The most reusable advice is not Miri-specific. The post says to keep secrets away from any job that can write to a shared cache, even if you do not use Miri, because many tools assume the whole environment can be written to disk. Cargo, Miri and Rust do not guarantee that environment variables stay out of `target/`, and build scripts can also store environment data in build artifacts.

For teams, that suggests a quick audit: which CI steps see secrets, which directories are cached, and whether untrusted PR code can read those caches. Splitting secret-bearing steps into separate jobs from cached build and test jobs is a small change that removes this whole class of problem.

The issue was reported by Predrag Gruevski of OpenAI, according to the post.
